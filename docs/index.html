Case study · local mail triage

Clearing the backlog without shipping it anywhere

A small rules-plus-local-LLM tool, built to fix one overloaded set of inboxes — published here de-identified, in case the approach is useful to someone else's.

This started as a request to unsubscribe from a pile of marketing email. It ended as a standing tool: something that classifies mail, catches buried events, questions its own spam filter, and never once sends, deletes, or posts anything without a person looking at it first.

The problem before

Seven personal and work mailboxes, years deep in unread marketing mail, an old auto-forwarding rule quietly duplicating messages across two of them, and — the part that actually mattered — real bank, pharmacy, and billing alerts sitting unread in a Junk folder next to the newsletters, because a spam filter can't tell "unfamiliar sender" from "important."

The approach how

Cheap header rules do the first pass — List-Unsubscribe, sender patterns, receipt-shaped subject lines — because most mail sorts itself instantly and for free. Anything the rules can't place, or that smells like it might contain a real event, goes to a small model running entirely on the machine. Nothing about the content of a message ever leaves it.

01

Unsubscribe queue

Ranks senders by real mailing-list signals, not guesswork. One-click (RFC 8058) where the sender supports it, a browser tab where they don't. Fires only after a person approves that specific sender.

02

Buried events

Reads for invitations, deadlines, and appointments hiding inside ordinary mail, cross-checks them against the calendar so nothing gets re-suggested, and waits for a yes before writing anything.

03

Spam audit

Added mid-project, after a manual check turned up real financial alerts in the spam folder. Now runs daily: flags receipt- and security-shaped mail sitting in Junk, with a phishing hint for spoofed senders — never moves anything without approval.

04

Daily digest

One page each morning: what's pending, what's noisiest, what needs a look. The whole reason the other three don't require remembering to check anything.

Field notes what broke, and why it's useful

The two bugs below cost the most time and are the most likely to bite anyone else scripting Apple Mail — worth naming precisely.

→ silent hang found day one

The obvious way to ask Mail for "messages since date X" is a predicate filter — whose({dateReceived: {greaterThan: cutoff}}). On a mailbox with tens of thousands of messages, that predicate can take minutes to evaluate, well past any script's patience, and it fails silently: a scheduled job just stops producing output, no error, no crash.

The fix was to stop asking Mail to filter at all. Pull the cheap properties — id, date, sender, subject — for every message in one bulk call (fast: under a second for thousands of messages), then filter in-process. Same result, no predicate, no hang.

→ mailbox names lie found in production

Apple Mail's mailbox lookup does a case-sensitive substring match with no error on a near-miss. Asking for a mailbox named Junk on an Exchange account silently resolves to Junk Email — and the reverse trips too: asking for INBOX where the real name is Inbox fails outright, since the cases don't overlap at all.

Two different failure shapes from the same root cause, both invisible until a message actually needed to move. The fix: never trust the name you asked for — read back whatever the lookup actually resolved to, and use that.

Why nothing here is risky safety model

Every action needs a yes

  • Read-only against the mailbox by default — classification never moves or deletes a message on its own.
  • An unsubscribe fires only after a person approves that specific sender, one at a time.
  • A calendar entry is written only after a person approves that specific event.
  • A "protect this sender" option exists everywhere a queue does, so a correct decision only has to be made once.
  • State lives in one file on the machine. Delete it, start clean, nothing to migrate.

Try the shape of it get started

The tool runs entirely local and MIT-licensed: github.com/retrogradespace/mailsweep-oss. But the shape of it travels even without the code: classify cheaply first, escalate only the ambiguous remainder to a model, and gate every write behind an explicit yes.

# the daily loop, in full
mailsweep scan            # classify new mail, queue candidates, write the digest
mailsweep unsub review    # y / n / protect, one sender at a time
mailsweep events review   # y / dismiss, one event at a time
mailsweep spam review     # rescue / leave / protect, one message at a time
